**Document ID:** RFT-EXP-SELC4-2026-001  
**Date:** 2026-08-03  
**Laboratory:** RFT-SIRM / UltraCore-RFT  
**Classification:** Reproducible Research Artifact  
**Revision:** Final

## 1. Abstract

This report documents a deterministic empirical verification experiment in which the UltraCore-RFT stress-testing methodology was applied to the Capability Derivation Tree (CDT) of the seL4 microkernel. The experiment executed more than one billion pseudo-random, syntactically valid capability operations under deterministic seed control. No kernel crashes, panics, or allocator-level invariant violations were observed during the monitored execution. The seL4 test suite completed successfully after the marathon phase.

This experiment does not claim to prove, improve, or replace the formal verification of seL4. It records only observable, reproducible behavior under sustained load.

---

## 2. Objective

To empirically observe the stability and resource reclamation behavior of the seL4 CDT implementation when subjected to a sustained sequence of valid capability invocations generated by a deterministic, seed-controlled pseudo-random process.

The experiment tests the following working hypothesis:

> *Under a deterministic pseudo-random sequence of syntactically valid capability invocations, the seL4 CDT implementation does not produce kernel panics, unrecoverable page faults, or VKA-level memory leaks detectable by the test harness.*

This hypothesis is empirically falsifiable and does not constitute a mathematical theorem about seL4 correctness.

| Parameter | Value |
|-----------|-------|
| Kernel | seL4 (as shipped with the sel4test testbed) |
| Architecture | ARM64 (aarch64) |

| Subsystem under observation | Capability Derivation Tree (CDT) |

| Test harness | sel4test framework (DEFINE_TEST) |

### 3.1 Operation families exercised

The experiment exercised the following seL4 capability operation families:

| Family | seL4 / VKA Primitive | Effect |
|--------|---------------------|--------|
| **Retype** | vka_alloc_object / seL4_Untyped_Retype | Materializes kernel objects from untyped memory into CNode slots |
| **Mint** | vka_cnode_mint / seL4_CNode_Mint | Creates a derived capability with an altered badge or reduced rights |
| **Copy** | vka_cnode_copy / seL4_CNode_Copy | Duplicates a capability, optionally with reduced rights |
| **Delete** | vka_cnode_delete + vka_free_object / seL4_CNode_Delete | Destroys a capability and, for original objects, reclaims backing memory |
| **Revoke** | vka_cnode_revoke / seL4_CNode_Revoke | Recursively destroys all capabilities derived from a specified capability |
| **Move** | vka_cnode_move / seL4_CNode_Move | Transfers a capability destructively from a source slot to a destination slot |
| **Mutate** | vka_cnode_mutate / seL4_CNode_Mutate | Alters a capability in place by applying a badge mask |
| **Rotate** | seL4_CNode_Rotate | Reorders three CNode slots atomically |
| **CancelBadgedSends** | seL4_Endpoint_CancelBadgedSends | Cancels pending sends on an endpoint matching a badge pattern |

The pseudo-random scheduler draws from these families according to a deterministic seed-controlled distribution. The exact per-family frequency is not fixed; it varies with the seed and the current state of the capability pool. The operation mix is therefore described as *stochastic within deterministic bounds* rather than by fixed percentages.

### 3.2 Object types retyped

Only the following object types were materialized during retype operations:

- seL4_EndpointObject
- seL4_NotificationObject
- seL4_TCBObject

Other object types (page tables, frames, ASID pools, device untypeds) were outside the scope of this experiment.

## 4. Methodology: Deterministic Empirical Verification

The experiment applies the UltraCore-RFT deterministic verification protocol to an external kernel subsystem. The protocol consists of five mandatory phases:

### 4.1 Deterministic seeding

Every batch is initialized with a computable seed:

```text
seed(batch_index) = 0x52465453 + batch_index
```

This ensures that the entire pseudo-random sequence is reproducible across identical builds.

### 4.2 Batch isolation

Each batch operates on a fresh logical state. The root CNode slot pool is reset to a known baseline before a batch begins. No capability state survives from one batch to the next.

### 4.3 Invariant telemetry

During each batch the harness records:
- ops_ok — invocations that returned seL4_NoError
- ops_fail — invocations that returned an expected error code (e.g., seL4_FailedLookup, allocator exhaustion)
- final_caps — number of live capabilities remaining in the tracked slot pool at batch end

### 4.4 Resource drain protocol

Every batch concludes with a mandatory teardown phase:
- Original objects are returned via vka_free_object
- Derived capabilities are deleted via vka_cnode_delete and their slots freed via vka_cspace_free
- The final_caps counter must read zero before the batch is accepted

### 4.5 Failure classification

ops_fail counts only *shallow rejections*: API calls that the kernel correctly refused because preconditions were not met (empty pool, missing source capability, etc.). These are normal return codes, not kernel faults.

## 5. Implementation

The fuzzer is implemented as a single C compilation unit integrated into the sel4test build tree:

```text
projects/sel4test/apps/sel4test-tests/src/tests/rft_cdt_fuzzer_sel4.c
```

### 5.1 Capability tracking

A fixed-size array (512 slots) tracks capabilities residing in the root CNode. Each entry records:
- cptr — slot address in the root CNode
- type — seL4 object type
- orig — boolean flag: original (retyped) vs. derived (copied, minted, moved, mutated)
- obj — complete vka_object_t structure required for correct deallocation of original objects

### 5.2 Constraints

- All invocations are syntactically valid and respect the seL4 ABI.
- No malformed capabilities, out-of-bounds arguments, or invalid encoding are injected.
- The fuzzer runs single-threaded inside one user process; no inter-CPU races are exercised.
- The experiment does not bypass any seL4 access-control checks.

| **Kernel crashes** | 0 |

| **VKA allocator inconsistencies** | 0 |
| **seL4 test suite post-marathon** | 123 / 123 passed |
| **RFT_CDT_MARATHON status** | Passed |

### 7.2 Per-batch telemetry

Across the marathon, batches exhibited the following stable pattern:
- ops_ok per batch: approximately 4 000 valid completions
- ops_fail per batch: approximately 6 000 expected shallow rejections
- final_caps post-drain: 0 in every batch

The ops_fail count reflects the stochastic nature of the scheduler: early in a batch, Delete, Revoke, Move, and Mutate operations frequently encounter empty or mismatched slots, producing expected seL4_FailedLookup or seL4_InvalidArgument returns. As the capability pool grows, the success rate rises. At no point did a failure manifest as a kernel fault or capability corruption.

### 7.3 System state after marathon

Following the marathon phase, the full sel4test suite was executed. All 123 tests completed without regression. No divergence from the pre-marathon baseline was detected.

## 8. Relationship to UltraCore-RFT

This experiment is **not** an attempt to prove, audit, or improve the seL4 microkernel. Its purpose is to demonstrate that the deterministic empirical verification methodology developed within the UltraCore-RFT / SIRM research program can be transferred from the blockchain runtime layer to the operating-system layer.

The SIRM core methodology consists of:
1. **Deterministic seed control** — every state transition sequence is reproducible
2. **Invariant telemetry** — quantitative metrics are recorded after every operation batch
3. **Resource drain verification** — the system must return to a known clean state
4. **Complementary checking** — empirical stress runs operate alongside, not instead of, formal specifications

By applying these four principles to the seL4 CDT, the experiment shows that the UltraCore-RFT verification protocol is **transferable** to external deterministic systems. The object of study is not seL4 itself, but the *applicability of the methodology*.

## 9. Research Contribution

The contribution of this work is **methodological**, not architectural. We do not claim to have:
- Found bugs in seL4
- Replaced or weakened formal verification
- Improved kernel performance or security
- Discovered new attack vectors

The actual contributions are:

1. **Deterministic empirical stress verification.** A seed-controlled, reproducible protocol for subjecting a capability-based kernel subsystem to sustained pseudo-random valid load.

2. **Repeatable capability verification methodology.** A documented procedure (build, run, drain, measure) that can be replicated by other researchers on identical or modified seL4 configurations.

3. **Complementary verification alongside formal proofs.** An empirical layer that checks runtime behavior against observable invariants (zero leaks, zero faults, clean teardown) without asserting coverage of the formal specification.

4. **CI-ready kernel regression methodology.** A lightweight fuzzing harness that can be integrated into continuous integration pipelines to detect regressions in CDT behavior after kernel modifications.

5. **Reusable research framework.** The implementation is a single-file drop-in module for sel4test. It can be adapted to other capability-based microkernels or to custom seL4 extensions (e.g., new capability types or policy layers) without rewriting the harness.

## 10. Limitations

The following limitations are stated explicitly to prevent over-interpretation:

1. **Empirical, not mathematical.** This experiment provides observational data. It does not constitute a formal proof of seL4 correctness, nor does it replace the existing Isabelle/HOL proof.

2. **Valid-input only.** Only syntactically correct, ABI-compliant invocations were used. Malformed system calls, invalid capability encodings, out-of-bounds arguments, and fuzzing of the kernel binary itself were excluded.

3. **Limited object coverage.** Only Endpoint, Notification, and TCB objects were retyped. Page tables, ASID pools, frame objects, IRQ control capabilities, and device untypeds were not tested.

4. **Single-threaded, single-address-space.** No concurrency, inter-CPU races, or multi-process capability transfers were exercised.

5. **Emulated hardware.** QEMU virt was used. Timing, cache behavior, and memory-ordering effects on physical silicon may differ.

6. **No temporal verification.** Real-time bounds, interrupt latency, and scheduler determinism were not measured.

7. **No security audit.** The experiment does not assess seL4 against threat models, side channels, speculative execution, or fault injection.

8. **Observational ceiling.** A zero-fault result over 10^9 operations does not imply that the 10^9+1-th operation cannot fail. It is a statistical sample, not an exhaustive enumeration.

---

## 11. Conclusions

1. The UltraCore-RFT deterministic empirical verification methodology was successfully applied to an external deterministic system — the seL4 microkernel Capability Derivation Tree.

2. Over **one billion** pseudo-random valid capability invocations, no observable deviation from expected kernel behavior was detected in the tested configuration. Memory was reclaimed correctly, no kernel faults were triggered by the harness, and the post-marathon sel4test suite completed without regression.

3. The experiment demonstrates that the SIRM verification protocol is transferable from blockchain runtime systems to operating-system subsystems, provided the target system exposes deterministic state transitions and measurable resource invariants.

4. The artifact is reproducible, seed-controlled, and suitable for regression testing of future seL4 modifications, including custom capability types and policy extensions.

5. The result **does not** constitute a proof of seL4 security, a replacement for formal verification, or an audit of the kernel. It is a recorded empirical observation under the specific constraints listed in Section 10.
